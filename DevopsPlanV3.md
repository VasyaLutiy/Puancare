# MVP `v3_meta_bios_pddl` — самовыращиваемый PDDL-домен

## Context

v2 (`v2-pddl-numeric`, HEAD `fab0274`) доказал механизм `propose → verify → amortize`:
агент учит **значения** (порог памяти, плохой config) внутри **рукописной** схемы
(`domain.pddl` + `ontology.yaml`). Боль, ради которой затеян v3: схема захардкожена —
предикаты, интервенции и их причинная проводка написаны человеком, поэтому код «не
масштабируется на другие домены».

**Гипотеза v3 (что демонстрирует MVP):** тот же доказанный механизм, поднятый на уровень
выше, способен **выращивать саму схему**. Стартуя с почти пустого домена, агент на каждом
**разрыве** (provals в песочнице) получает от LLM *кандидат-фрагмент* схемы (предикат +
интервенция + тип переменной) под фиксированную мета-грамматику, **проверяет** его
интервенцией в Docker, и **амортизирует** подтверждённое в meta-BIOS. `domain.pddl`
**генерируется** из реестра интервенций, не пишется.

**Критерий, отличающий самообучение от дорогого LLM-lookup'а** (§8 для v3): число
LLM-вызовов **на задачу** должно падать до 0 по мере накопления схемы. Если каждая новая
задача требует свежего дампа от LLM — это LLM-фронтенд, и хороним честно.

**Решения пользователя (зафиксированы):**
- **Gap-driven:** LLM зовётся только в момент разрыва, за недостающий фрагмент. Не «вся схема наперёд».
- **Живой LLM + replay:** headline-демо и фальсификатор — на живом Azure; записанный replay-режим для быстрой регрессии без токенов.
- **Граница, как в v2:** планировщик владеет логикой (секвенирование, достижимость), обучение владеет величинами (значение памяти/конфига подаёт агент-политика, не план).
- **Мета-уровень — цикл, не PDDL.** Эпистемический планировщик («какую пробу ставить») остаётся отложенным. PDDL генерится только на **объектном** уровне (домен, что растёт).

## Подход

Новый изолированный подпакет `devops_agent/v3/` — v2 не трогаем. Переиспользуем песочницу,
LLM-транспорт и вызов планировщика как есть; новое — мета-грамматика, генератор домена,
proposer и петля-выращиватель.

### Семя (рукописное — это грамматика, не словарь)

Единственное, что задаётся руками и доменно-независимо:
1. **Мета-грамматика** — 6 типов как JSON-схема для `AzureJSON.ask(schema=…)`.
2. **Цель** — предикат `(running ?s)`.
3. **Терминальная интервенция `deploy`** со **стартово пустым** списком предусловий
   (только `(not (running ?s))`) — её преконды **дорастают** по мере чеканки предикатов.
4. **Поверхность рычагов** (актуаторы) — то, что агент умеет дёргать в мире: `set memory=N`,
   `set config=X`. Берётся из `agent_view()` (config_options + current_config) + известного
   «можно задать память». Это честно: в реале список рычагов — это API платформы, он дан и
   интроспектируем. Дефолт config-рычага = унаследованный `current_config` (закон
   «unknown→verify→trust»: агент действует по наследству, мир опровергает).

Что **НЕ** задаётся и выучивается: предикаты (`mem_ok`, `config_ok`), их проводка в
преконды/эффекты `deploy`, и стратегия разрешения переменной. MVP наглядно **реконструирует**
рукописный `domain.pddl` v2 из нуля — но порождённо, и проверяет, что он обобщается.

### Раскладка модулей

```
devops_agent/v3/
  meta_schema.py    # 6 мета-типов (dataclasses) + JSON-схема для LLM + валидатор. Фикс. семя.
  meta_bios.py      # MetaBios: выращенный домен (actuators, predicates, intervention-registry,
                    #   strategy-по-переменной, covered_symptoms, выученные значения, счётчик llm_calls).
  domain_gen.py     # реестр интервенций → текст domain.pddl + problem.pddl (форма v2: types/predicates/actions).
  strategies.py     # библиотека стратегий по типу переменной: ordered_monotone→doubling,
                    #   categorical→enumerate-incumbent. (порт v2-петель из agent.py/_choose_config)
  proposer.py       # SchemaProposer: Live (AzureJSON.ask, cost-gated, счёт токенов) + Replay (фикстуры).
  meta_agent.py     # ПЕТЛЯ: gen-domain → solve → act → gap → (cache? | propose) → wire → verify → amortize → replan.
  harness_v3.py     # §8-для-v3: кривая llm_calls/задача ↓; детерминизм; novel-task фальсификатор.
  fixtures/         # записанные LLM-ответы для replay-регрессии.
```

### Мета-грамматика и канонизация имён (ключевое решение)

LLM на разрыве возвращает НЕ вольный PDDL, а **дискриминатор** под `AzureJSON.ask(schema=…)`:

```
{"dimension":      "<ключ рычага из ДАННОЙ поверхности актуаторов, что разрешает симптом>",
 "kind":           "ordered_monotone | categorical | boolean",   # → выбор стратегии
 "predicate_name": "<человекочитаемое имя, для лога>",
 "rationale":      "<одна строка>"}
```

- Имя PDDL-предиката **выводится из рычага** (`{dimension}_ok`, напр. `mem_ok`), НЕ из текста LLM →
  убивает синонимию (`mem_ok` vs `memory_sufficient`) и даёт **детерминизм** домена.
- LLM предлагает СЕМАНТИКУ (какой рычаг ↔ какой симптом ↔ какой kind) — это гипотеза, фальсифицируемая
  песочницей: неверный kind (напр. «удваивать config») не сойдётся → опровергнут.
- `domain_gen` из реестра собирает: `(:predicates (running ?s) (mem_ok ?s) (config_ok ?s) …)`,
  по одному `(:action set_<dim> … :effect (<dim>_ok ?s))`, и `deploy` с преконд = конъюнкция всех
  `deploy_requires`. Объект-проблема тривиальна (`:objects goal_svc - service`, `:goal (running …)`).
  Значение рычага (память N, config X) даёт **агент-политика**, не план (граница v2).

### Петля (meta_agent.py) — обобщение v2 `agent.py`

1. `domain_gen` → `domain.pddl`+`problem.pddl` из текущего MetaBios; решить
   `PDDLReader().parse_problem` + `OneshotPlanner("fast-downward-opt")` (копия вызова из `bios.plan`).
   План тривиален, но **доказывает разрешимость сгенерённого домена** и секвенирует `set_*→deploy`.
2. Выбрать значения рычагов: где есть стратегия → стратегия, иначе → дефолт актуатора (mem=64, config=incumbent).
3. `World.apply({service, mem_bucket, config})`. `running` → записать пороги/incumbent, амортизировать, успех.
4. **Разрыв** (`phase != running`): `symptom = wm.classify(obs)`.
   - **covered_symptoms[symptom] = D (кэш):** применить шаг стратегии D (удвоить mem / следующий config /
     mark_bad) → replan. **0 LLM** (зеркало v2 reverse_index).
   - **холод:** `proposer.propose(symptom, ctx, known_actuators)` → mint_dimension(D,kind,name):
     добавить предикат + `set_D` + `deploy_requires += D_ok` + `strategies[D]=kind` +
     `covered_symptoms[symptom]=D`; `llm_calls += 1`. Применить шаг стратегии → replan.
   - **verify/refute (грубый, MVP):** неверная гипотеза ведёт к исчерпанию стратегии (ceiling по памяти /
     все config плохи) → эпизод падает «refuted: D не разрешил S» → снять mint + `covered_symptoms[S]`,
     перепредложить с пометкой опровержения (1 ретрай). Happy-path не триггерит; ветка покрыта unit-тестом
     с заведомо неверной replay-фикстурой. Тонкий info-gain-refute отложен.

### §8 для v3 (harness_v3.py) — стиль run_experiment.py

Поток задач: `[mem/A (холод), mem/B (перенос), cfg/svc_e (холод-setting), cfg-повтор (перенос), combined-novel (F′)]`.
Метрика: кривая `llm_calls` на задачу. Ожидаемо `[1, 0, 1, 0, 0]`.

**Вердикт ЖИВ/ХОРОНИМ:**
1. **Перенос:** `llm_calls(перенос) < llm_calls(холод)` того же структ-класса (в идеале 0).
2. **Амортизация:** после холодного всплеска каждого класса хвост → 0.
3. **Детерминизм:** повтор полного прогона → **идентичный** сгенерённый `domain.pddl`
   (канонизация имён это гарантирует; сравниваем нормализованный текст, не вывод LLM).

**Novel-task фальсификатор (F′, аналог секции F):** сервис, которому нужны **И память, И config**,
никогда не виденный, инъекция **только данными** (приём из run_experiment: `_SERVICES[...] = {...}` в
рантайме + cleanup). Должен сойтись с **0 новых LLM-вызовов** (обе схемы уже выучены). Если потребовал
свежий LLM — харнесс печатает «не обобщается», и это **часть вердикта**, не маскируется.

**Гварды:** сгенерённый `domain.pddl` без чисел/`:metric` (наследие #8 не вернулось — grep);
`mem_ok`/`config_ok` **отсутствуют** в семени (доказ., что порождены, не вписаны — grep семени).

1. **Replay-selftest (без токенов):** `venv/bin/python -m devops_agent.v3.meta_agent --selftest`

## Scope cuts / честные ограничения (печатает харнесс)

- Активны 2 мета-типа: **Resource** (память, ordered→doubling) и **Setting** (config, categorical→enumerate).
  **Dependency** (взаимодействие сервисов — где оживает планировщик) и **темпоральные агрегаты** — вне MVP.
- **Синонимия предикатов** не решается общим ontology-alignment: имена выводятся из рычага (`bound_to`),
  достаточно для 2 измерений. Полная консолидация отложена.
- **Refute грубый** (исчерпание стратегии), info-gain-выбор пробы отложен.
- LLM заведомо знает про память/config — это **ожидаемо** и не порок: он генератор гипотез; доказывает
  не «LLM глуп», а кривая `llm_calls → 0` (амортизация) + F′ с 0 новых вызовов.
- Сенсор (`exit_code → симптом`) в MVP остаётся минимально заданным (читает вывод актуатора); обучение
  сенсорики — следующий заход. Новый структ-класс (напр. disk) требует нового симптома → правок world.py.
- Мета-управление — цикл; эпистемический планировщик отложен (как в DevopsPlanV2 §«Открытый вопрос»).

## Критерий убийства (без послаблений)

Кривая `llm_calls`/задача **не** падает к 0, ИЛИ F′ требует свежего LLM, ИЛИ перенос не работает →
это LLM-фронтенд, не самообучение. Хороним честно, не подгоняем под зелёное. Судья — Docker, не LLM.
