# CAUSAL-01: приватный протокол испытаний — живой чек-лист

> **Статус:** пробный экзамен `pilot-001` принят 2026-07-27; E0–E5 — PASS.
> Это отладочный результат одного мира, не подтверждение общей гипотезы и не
> зачёт official-партии.
>
> **Конфиденциальность:** это частный документ исследователя и независимого
> экзаменатора. Его нельзя целиком передавать разработчику: разработчик получает
> только публичный контракт, собственные тестовые fixtures и результаты уже
> раскрытых проверок. Закрытые seed, oracle, таблицы соответствий twin-пар,
> held-out состояния, salt и критерии конкретной партии не передаются до
> вердикта.

## 1. Цель, узкое утверждение и границы

- [ ] Зафиксировать узкое утверждение: в детерминированном игрушечном мире
  learner сначала применяет один ложный prior `A → C / cochanges`, затем по
  собственным переходам опровергает его, открывает истинное `A → B`, переживает
  перезапуск и точно прогнозирует ранее не виденный переход.
- [ ] Считать доказанным только это утверждение о правиле перехода пяти
  наблюдаемых двоичных переменных, а не «понимание причинности» в общем смысле.
- [ ] Не расширять вывод на скрытые переменные, шум, вероятности, несколько
  причин, язык имён, поиск кода, планирование, LLM или перенос между иными
  грамматиками мира.
- [ ] Зафиксировать бюджет каждой жизни: не более 8 вызовов `step`; успех
  возможен только с полностью сохранённой историей ложной гипотезы.

## 2. Непроницаемая граница «публичный атлас — частный oracle»

- [ ] Learner получает только байты `atlas.yaml` и capability/RPC
  `observe()`, `action_space()`, `step(action_id)` из `CAUSAL_WORLD_PROTOCOL/v1`.
- [ ] Проверить, что wire-ответ `observe()` содержит только
  `variable_id → value`, `action_space()` — публичные описания действий, а
  `step()` — только `action_id`, машинный `outcome` и `obs_after`.
- [ ] Проверить отсутствие в learner-visible сообщениях полей `effects`,
  `truth_fn`, ролей, диагностических объяснений, путей, traceback и содержания
  оракула; learner сам вычисляет diff `before/after`.
- [ ] Запускать learner в отдельном процессе, с чистым environment, отдельным
  working directory и без oracle-каталога или examiner-модулей в import path.
- [ ] Добавить отрицательную проверку: намеренная попытка learner прочитать,
  импортировать или вывести oracle должна аннулировать весь прогон независимо
  от счёта E0–E6.
- [ ] Хранить oracle, generator seed и salt только у экзаменатора; не коммитить
  их в рабочую ветку, тестовые fixtures или логи, доступные до раскрытия.

## 3. Контракт генератора: CAUSAL-профиль `transition-atlas/v1`

- [ ] Генерировать ровно пять observable-переменных с доменом из двух разных
  JSON-скаляров каждая, ровно два действия `toggle` с разными target и ровно
  одну исходную гипотезу `cochanges`.
- [ ] Выдавать именно `schema: transition-atlas/v1`; не подменять его
  несовместимым названием схемы или незафиксированным «causal» форматом.
- [ ] Устанавливать policy без исключений:
  `support_min: 2`, `refute_min: 2`,
  `candidate_generation: all_observable_effects`,
  `proposed_prediction: changed`.
- [ ] Делать ложный prior ровно `A → C / cochanges` с provenance `atlas`; до
  опыта в публичном атласе не должно быть `A → B` и иных гипотез.
- [ ] Сделать истинный переход действия в `A`: меняются ровно `A` и скрытый
  истинный эффект `B`; `C`, `D` и `E` не меняются.
- [ ] Сделать контрольный переход действия в `D`: меняется только `D`; `A`,
  `B`, `C`, `E` не меняются.
- [ ] Обеспечить два успешных запуска каждого действия из противоположных
  значений его target; отклонять мир, где истинная и ложная гипотезы дают один
  наблюдаемый прогноз.
- [ ] Не включать `initial_state` в atlas: первое авторитетное состояние
  доступно learner только из `observe()`.

## 4. Слепые публичные скелеты и twin-пары

- [ ] Сначала построить публичный структурный скелет ролей `A`, `C`, `D`, `U`,
  `V`: prior связывает `A → C`, действие в `A`, действие в `D`; роли `U` и `V`
  публично неразличимы и не имеют предметных имён.
- [ ] Только после фиксации байтов публичного atlas назначить в закрытом oracle
  один из `U/V` скрытой ролью `B` (true effect), а другой — скрытой ролью `E`
  (decoy); это назначение никогда не попадает в atlas.
- [ ] Для каждой counterfactual twin-пары создать **байтово идентичный**
  публичный atlas: различается лишь приватный oracle, где `U` и `V` меняются
  ролями `B` и `E` как истинный эффект/приманка.
- [ ] Генерировать opaque id переменных, id действий и значения в заранее
  фиксированном машинном формате (без слов, префиксов и смысловых подсказок);
  не использовать их лексический порядок как семантику.
- [ ] Для каждого мира независимо переставлять порядок YAML mapping и всех
  коллекций, порядок domain-значений, порядок действий и полярность каждого
  двоичного домена; после обратного переименования структурный результат обязан
  совпасть.
- [ ] Проверить, что сами перестановки не меняют канонический atlas identity,
  а полярность/переименование не дают learner подсказку о скрытой роли.

## 5. Инварианты генератора и атласа

- [ ] Валидировать `safe_load`, отсутствие небезопасных YAML-конструкторов,
  рекурсивных aliases, неизвестных полей и начального состояния.
- [ ] Валидировать точные коды E0-входов: `SCHEMA_VERSION`, `DUPLICATE_ID`,
  `BAD_DOMAIN`, `BAD_ACTION_TARGET`, `BAD_HYPOTHESIS_ENDPOINT`,
  `UNKNOWN_RELATION`, `INITIAL_STATE_FORBIDDEN`, `UNKNOWN_FIELD`,
  `BAD_EXPERIMENT_SHAPE`.
- [ ] Проверить `BAD_EXPERIMENT_SHAPE`: ровно 5 observable binary variables,
  ровно 2 разных `toggle` target, единственный prior `cochanges` с разными
  endpoint, cause является target ровно одного действия, лишних hypotheses нет.
- [ ] Проверить, что materialization кандидатов охватывает все остальные
  observable effects выбранной причины, в том числе неизменившиеся переменные,
  и первый переход применяется к каждому кандидату ровно один раз.
- [ ] Проверить content-id как SHA-256 canonical JSON массива
  `[cause, effect, relation]`, а `source_ref` — отдельно от внутреннего id.
- [ ] Проверить canonical shelf: UTF-8, sorted keys, compact JSON, hypotheses
  по content-id, experiences/evidence по числовому id; атомарное сохранение и
  `load → save → load` без опыта побайтно идентичны.
- [ ] Проверить append-only опыта и evidence, одну монотонную версию на
  принятый переход, точные integer-счётчики и сохранение `refuted` гипотезы.
- [ ] Проверить commitment chain/`informative`: все обязательные SHA-256 поля
  согласованы, `informative` — committed JSON boolean; неинформативный переход
  записывается, но не создаёт кандидатов и не меняет evidence.

## 6. Фазы испытаний

### 6.0 Пробный экзамен: один мир (не зачёт)

- [x] Сгенерировать один публичный `atlas.yaml` и соответствующий ему приватный

- [x] Провести полный lifecycle пробного экзамена, включая прогноз до действия,

- [x] Сохранить транскрипт, shelf до/после restart и отчёт E0–E5; результат

- [ ] После разбора результата отдельно принять решение о twin gate,
  запечатывании oracle, хранителе закрытых данных и independent scorer.

### 6.1 Аудит генератора

- [ ] Выполнить независимую проверку инвариантов разделов 3–5 до запуска

- [ ] Сформировать проверяемый отчёт, что в каждой паре публичные atlas bytes

### 6.2 Разработческий контур (не зачёт)

- [ ] Дать разработчику только открытые, не входящие в official-партию fixtures
  и публичный API; не раскрывать twin mapping, hold-out, salt или seeds.
- [ ] Проверить lifecycle отдельными шагами: `bind/observe → predict → step →
  accept_transition`, без комбинированного метода, который может записать
  прогноз задним числом.

### 6.3 Невалидные fixtures

- [ ] Для каждого кода из раздела 5 подготовить отдельный fixture и проверить
  машинный код/JSON Pointer, не текст ошибки.
- [ ] Проверить отказ до частичного изменения shelf или pending prediction.

### 6.4 Metamorphic-проверки

- [ ] На публичных тренировочных мирах проверить переименование всех id и
  значений, перестановки YAML/коллекций, инверсию полярности и повторный
  save/load.
- [ ] После обратного канонического переименования сравнить hypotheses,
  статусы, evidence, прогноз и структурную последовательность действий; не
  сравнивать случайный исходный порядок строк.

### 6.5 Квалификация twin-пар

- [ ] Для каждой пары подтвердить: публичный atlas не позволяет отличить `U`
  от `V` до вмешательства в `A`, оба оракула допустимы и дают разные истинные
  эффекты на том же публичном входе.
- [ ] Подтвердить, что prior `A → C` одинаково ложен в обоих близнецах, а
  замена одного oracle на другой не меняет ни байта learner-visible входа.

### 6.6 Официальная партия

- [ ] Запечатать ровно 12 квалифицированных twin-пар = **24 независимых
  прогона**; для каждого прогона использовать отдельный процесс и чистое
  persistent state.
- [ ] Не заменять официальный критерий средним результатом по 12 мирам:
  каждому из 24 прогонов требуются E0–E6 и все условия twin-квалификации.

## 7. Обязательная жизнь одного мира: `A, A, D, D`, смерть, reload, held-out

- [x] До первого `step(A)` запросить и зафиксировать прогноз: `C` должен быть
  заявлен изменяющимся по prior, а `A → B` не должен быть заявлен как уже
  известный факт.
- [x] Выполнить успешный цикл `A` из одного значения target: прогноз до шага,
  raw `step`, immutable evidence, атомарное обновление кандидатов.
- [x] Выполнить второй успешный `A` из противоположного значения target;
  это обязано дать второе независимое свидетельство для `A → B` и против
  `A → C`.
- [x] Выполнить `D` и повторный `D` из противоположного значения target;
  доказать отрицательный контроль и вторично опровергнуть `D → A/B/C/E`.
- [x] Не использовать больше четырёх успешных обязательных вмешательств;
  допускаются только явно журналируемые неуспехи/повторы в общем лимите 8.
- [x] После E3 завершить learner-процесс, запустить новый и загрузить shelf:
  hypotheses, статусы, evidence, версия и canonical JSON должны совпасть
  бит-в-бит без дообучения.
- [x] После reload считать старое `current_observation` только audit-данными
  `stale/unbound`; до нового `observe()` прогноз запрещён, новое `observe()`
  не создаёт evidence и не увеличивает версию.
- [x] Подключить новый экземпляр того же oracle в закрытом ранее не встреченном
  допустимом состоянии; learner узнаёт его только первым `observe()`.
- [x] До held-out `step(A)` потребовать точный прогноз: changed `{A, B}` и
  unchanged `{C, D, E}`, без `unknown`; после шага сравнить с raw observation.

## 8. Проверочные утверждения E0–E6

- [x] **E0 — контракт и round-trip:** валидный atlas принимается, каждый
  невалидный fixture получает точный машинный code, порядок YAML не меняет
  загруженную форму, shelf round-trip канонически идентичен.
- [x] **E1 — prior усвоен:** до первого действия прогнозирует изменение `C`
  вместе с `A` и не выдаёт `A → B` за заранее известную связь; случайно верный
  стартовый прогноз считается провалом.
- [x] **E2 — опыт неизменяем:** для каждого действия существуют предшествующий
  прогноз, полный `before/action/outcome/after`, comparison и commitment;
  reload не меняет старые записи.
- [x] **E3 — самокоррекция в бюджете:** не позднее шага 8 `A → C` — `refuted`
  с `contradicts ≥ 2` из двух состояний `A`; `A → B` — experience-originated
  `supported`, `supports ≥ 2`, `contradicts = 0`, с двумя evidence; ложная
  гипотеза физически остаётся на shelf.
- [x] **E3 — закрытая грамматика:** `A → D/E` и `D → A/B/C/E` опровергнуты
  двумя наблюдениями каждый; статусы следуют только из `cochanges` и порогов
  2/2, без float и без исключений по id.
- [x] **E4 — смерть процесса:** новый процесс загружает идентичный shelf, не
  использует stale observation как текущую истину и может продолжить только
  после bind/observe нового мира.
- [x] **E5 — held-out:** на скрытом новом допустимом состоянии до шага верно
  классифицируются все пять переменных без `unknown`, после шага прогноз
  совпадает с наблюдением.
- [ ] **E6 — семейство:** в каждой из 12 twin-пар меняются opaque имена,
  действия, значения, порядок и полярность; после обратного переименования
  результат изоморфен, а абсолютный отчёт показывает **24/24**, не процент.

## 9. Заморозка, commitment, раскрытие и независимая оценка

- [ ] До генерации official-партии зафиксировать SHA-256 проверяемого learner
  кода, зависимостей, конфигурации, лимита 8, policy 2/2 и данного протокола.
- [ ] Независимый examiner после code freeze генерирует закрытую партию и
  публикует перед стартом манифест только с разрешёнными публичными atlas
  SHA-256, runner version и параметрами запуска.
- [ ] До official-запуска examiner публикует salted commitment закрытой партии;
  oracle, seed и salt не раскрываются до подписанного вердикта.
- [ ] Сохранять raw JSONL-транскрипты каждого RPC/прогноза/перехода и отдельные
  метаданные процесса; до раскрытия в них допускаются лишь opaque данные.
- [ ] Передать transcript и frozen manifest независимому scorer, который не
  участвует в разработке и не имеет права изменять критерии после запуска.
- [ ] После вердикта раскрыть salt, seed, oracle и mapping twin-пар; любой
  желающий должен суметь проверить commitment, публичные хэши, счёт и E0–E6.
- [ ] Отдельно пометить, что внутренние SHA-256 shelf commitments выявляют
  порчу/несогласованность, но не аутентифицируют злоумышленника, способного
  переписать весь snapshot; для такой угрозы нужен внешний signature/HMAC.

## 10. Защита от хардкода: отрицательные learner и мутации

- [ ] Прогнать заведомо плохой learner, который всегда объявляет `U` истинным
  эффектом; он обязан проиграть противоположного twin при идентичном atlas.
- [ ] Прогнать симметричный learner, всегда выбирающий `V`; он обязан
  проиграть другого близнеца.
- [ ] Прогнать learner с ветвлением по id, позиции YAML, domain-полярности,
  atlas SHA-256 и таблице правильных рёбер; каждый вариант обязан быть пойман
  permutation/twin/изоляционными тестами и аннулирован.
- [ ] Мутировать корректный learner: удалить E1-прогноз, удалить evidence,
  удалять `refuted` гипотезу, записывать прогноз после `step`, пропустить
  reload, принять oracle-импорт, разрешить `unknown` в E5; каждая мутация
  обязана нарушить свой гейт.
- [ ] Проверить, что evaluator не принимает частичный успех, lookup по полному
  atlas или «правильный ответ без различающих переходов».

## 11. Правило вердикта и известные ограничения утверждения

- [ ] Объявить **PASS только при 24/24**: все 24 официальных прогона проходят
  E0–E6, twin-квалификацию, oracle-изоляцию, lifecycle `A,A,D,D`, restart и
  held-out; любой `23/24`, утечка oracle, мутация без обнаружения или
  некорректный commitment означает FAIL.
- [ ] При FAIL опубликовать raw наблюдаемый результат и слой сбоя, но не
  ослаблять задним числом бюджет, пороги, fixture или критерий.
- [ ] Зафиксировать ограничение: `cochanges` подтверждает только устойчивое
  правило изменения в этом детерминированном закрытом стенде, не общую
  идентификацию причинности и не контрфактуал вне специально построенных twins.
- [ ] Зафиксировать ограничение: 24 прогона подтверждают устойчивость к
  указанным переименованиям/перестановкам, но не исключают все возможные
  способы хардкода и не доказывают безопасность произвольного кода.

## 12. Решения, требующие владельца

- [x] **Последовательность испытаний утверждена:** сначала один пробный экзамен
  без зачётного статуса; проектирование official-партии — только после его
  разбора. Владелец решения: исследователь/заказчик.
- [ ] **Twin gate — отложен до пробного экзамена:** проводить official
  оценку только как 12 байтово-идентичных public-atlas twin-пар (24 runs), а
  не как 12 одиночных миров. Владелец решения: исследователь/заказчик.
- [ ] **Запечатывание и хранитель oracle — отложены до пробного экзамена:**
  назначить независимого человека
  или процесс, который единолично генерирует, хранит и раскрывает oracle/salt
  после вердикта; разработчик этой ролью быть не должен.
- [ ] Утвердить исполнителя official-run и независимого scorer до code freeze.
- [ ] Утвердить место хранения зашифрованных закрытых артефактов и процедуру
  их уничтожения/архивации после воспроизводимого раскрытия.
