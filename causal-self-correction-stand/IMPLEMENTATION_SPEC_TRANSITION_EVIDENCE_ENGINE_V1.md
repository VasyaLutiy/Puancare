# ТЗ разработчику: универсальный движок свидетельств о переходах v1

## 1. Задача

Реализовать изолированный детерминированный Python-компонент, который:

1. загружает декларативное описание наблюдаемых переменных, действий,
   начальных утверждений и политики оценки;
2. принимает наблюдения переходов `before → action → after`;
3. сопоставляет каждый переход с проверяемыми утверждениями;
4. накапливает подтверждающие и противоречащие свидетельства;
5. строит прогноз до выполнения следующего действия;
6. сохраняет состояние на диск и полностью восстанавливает его после
   перезапуска.

Компонент не должен зависеть от конкретного входного YAML, имён сущностей,
числа переменных, числа действий, порядка полей или конкретных значений.

## 2. Границы задачи

В реализации v1 требуются:

- парсинг и строгая валидация входной схемы;
- модель утверждений и свидетельств;
- встроенный тип отношения `cochanges`;
- детерминированное порождение кандидатов;
- прогнозирование результата действия;
- append-only журнал переходов;
- каноническая сериализация и атомарное сохранение;
- абстрактный порт взаимодействия с внешней средой;
- unit-, property- и integration-тесты.

Не требуются:

- LLM, prompts, embeddings или внешние AI API;
- UI, HTTP-сервер и база данных;
- вероятностное обучение;
- оптимизация порядка действий;
- изменение `organism2.py`, `shelf.py` или существующего поведения
  FormDevourer.

## 3. Технологические ограничения

- Python той же версии, которая используется текущим репозиторием.
- Единственная разрешённая новая runtime-зависимость — `PyYAML`.
- YAML загружается только через `yaml.safe_load`.
- Произвольные YAML tags, Python object constructors и циклические aliases
  должны отклоняться.
- Никаких сетевых вызовов.
- Результат должен быть детерминированным.
- Новая реализация размещается в отдельном модуле/каталоге и не подменяет
  существующие классы проекта.

До написания кода предоставить короткую записку с предлагаемыми именами
модулей и публичными Python-интерфейсами.

## 4. Входной документ

### 4.1 Логическая схема

```yaml
schema: transition-atlas/v1

variables:
  - id: <opaque-string>
    domain: [<scalar>, <scalar>, ...]
    observable: true

actions:
  - id: <opaque-string>
    intervention:
      variable: <variable-id>
      operation: <opaque-operation-string>

hypotheses:
  - id: <source-local-id>
    cause: <variable-id>
    effect: <different-variable-id>
    relation: cochanges
    provenance: atlas

policy:
  support_min: <positive-integer>
  refute_min: <positive-integer>
  candidate_generation: all_observable_effects
  proposed_prediction: changed | unknown  # optional; default: unknown
```

Идентификаторы, значения доменов и operation являются непрозрачными данными.
Алгоритм не должен извлекать из строк семантику, сортировочный приоритет или
ожидаемый ответ.

### 4.2 Общие ограничения схемы

- переменных: не менее 2;
- действий: не менее 1;
- начальных утверждений: 0 или более;
- домен каждой переменной содержит не менее двух уникальных JSON-scalar
  значений;
- все `id` уникальны внутри своей коллекции;
- target действия обязан ссылаться на существующую observable-переменную;
- cause/effect обязаны существовать и различаться;
- дубликаты структурно одинаковых утверждений запрещены;
- неизвестные поля и неизвестные relation отклоняются;
- `policy.proposed_prediction` при отсутствии разрешается как `unknown`; при
  наличии допускаются ровно строковые `changed` или `unknown`;
- неверный тип/значение `policy.proposed_prediction` даёт `BAD_POLICY` по пути
  `/policy/proposed_prediction`, а иной неизвестный ключ policy —
  `UNKNOWN_FIELD` по его JSON Pointer;
- эффективное, включая default, значение `proposed_prediction` входит в
  canonical atlas и `atlas_id`;
- исходного состояния в atlas нет;
- порядок mappings и элементов коллекций не несёт смысла.

Валидатор не должен вводить верхние ограничения, привязанные к fixtures:
никаких проверок вида «ровно N переменных», «ровно M действий» или
«обязателен конкретный id».

### 4.3 Машинные коды ошибок

Минимальный набор:

- `SCHEMA_VERSION`;
- `DUPLICATE_ID`;
- `BAD_DOMAIN`;
- `BAD_ACTION_TARGET`;
- `BAD_HYPOTHESIS_ENDPOINT`;
- `DUPLICATE_HYPOTHESIS`;
- `UNKNOWN_RELATION`;
- `UNKNOWN_FIELD`;
- `INITIAL_STATE_FORBIDDEN`;
- `BAD_POLICY`;
- `CYCLIC_YAML`.

Публичный exception должен содержать код и путь до проблемного поля. Текст
сообщения не является стабильным API.

Runtime-валидация дополнительно использует коды `OBSERVATION_SHAPE`,
`VALUE_OUT_OF_DOMAIN`, `ACTION_NOT_AVAILABLE`, `OBSERVATION_UNBOUND`,
`PREDICTION_REQUIRED`, `PREDICTION_MISMATCH` и `DUPLICATE_EXPERIENCE`.
Полное наблюдение содержит каждую объявленную observable-переменную ровно один
раз, не содержит неизвестных ключей, а каждое значение входит в её domain.

## 5. Публичный lifecycle API

Конкретные Python-имена согласуются до кода, но доменный API обязан выражать
следующие операции без объединяющего метода «сделать всё»:

```text
create(atlas_bytes) -> engine
load(snapshot_path, atlas_bytes) -> engine
bind_observation(observation) -> None
predict(action_id) -> immutable_prediction
accept_transition(prediction_id, step_response) -> experience_id
snapshot() -> canonical_state
save(snapshot_path) -> None
```

`accept_transition` принимает только ранее сохранённый prediction id для того
же action и текущего `before`. Отсутствующий, повторный или несовпадающий
прогноз отклоняется без частичного изменения shelf. Это обеспечивает
проверяемый порядок `predict → step → accept_transition`.

## 6. Семантика v1

### 6.1 Переход

Информативный переход содержит:

- полное наблюдение `before`;
- выбранное действие;
- машинный outcome внешней среды;
- полное наблюдение `after`.

Запрошенное действие не считается выполненным автоматически. Переход
информативен только если target-переменная действия действительно сменила
значение между `before` и `after`. Неинформативный переход сохраняется в
журнале, но не меняет счётчики утверждений.

### 6.2 Отношение `cochanges`

Для утверждения `cause → effect / cochanges`:

- cause изменилась и effect изменилась: `supports += 1`;
- cause изменилась и effect не изменилась: `contradicts += 1`;
- cause не изменилась: счётчики не меняются.

Сравнивается только факт изменения значения. Равенство значений разных
переменных, их строковое представление и позиция значения в domain не
используются.

Архитектура relation evaluator должна допускать регистрацию новых типов
отношений без изменения shelf/persistence слоя. Реализовывать другие отношения
в v1 не требуется.

### 6.3 Порождение кандидатов

После первого информативного перехода для target-причины должны существовать
кандидаты `cause → X / cochanges` для каждой другой observable-переменной `X`.

Операция атомарна:

1. материализовать недостающие кандидаты;
2. применить текущий переход ко всем кандидатам этой причины ровно один раз;
3. пересчитать их статусы;
4. создать одну новую версию состояния.

Начальное утверждение с той же структурной тройкой переиспользуется, а не
дублируется.

### 6.4 Идентификатор утверждения

Внутренний `id` вычисляется одинаково для входных и созданных утверждений:

```text
sha256(canonical_json([cause, effect, relation]))
```

Исходный `hypotheses[].id` хранится отдельно как `source_ref`. Логика не
должна ветвиться по `source_ref`.

### 6.5 Статусы

Счётчики являются целыми числами и не преобразуются в float.

- `supported`, если `supports >= policy.support_min` и `contradicts == 0`;
- `refuted`, если `contradicts >= policy.refute_min`;
- иначе `proposed`.

Опровергнутое утверждение не удаляется и сохраняет все ссылки на
свидетельства.

### 6.6 Прогноз

Прогноз строится до вызова внешнего `step()` и после записи не редактируется.
Для выбранного действия результат содержит три непересекающихся множества
variable id:

- `changed`: target действия и его `supported` effects;
- `unchanged`: его `refuted` effects;
- `unknown`: effects со статусом `proposed` или с конфликтом.

Эффективная policy `proposed_prediction: unknown` (default) сохраняет
proposed/conflicted observable effects в `unknown`; `proposed_prediction:
changed` помещает их в `changed`. В прогноз могут входить только
observable-переменные: non-observable endpoint никогда не нарушает это
разбиение. Каждая observable-переменная обязана попасть ровно в одно множество.
При неизвестном текущем наблюдении прогноз запрещён машинной ошибкой
`OBSERVATION_UNBOUND`.

## 7. Модель постоянного состояния

Логическое содержимое shelf:

```yaml
schema: transition-shelf/v1
version: <monotonic-integer>
atlas_id: <sha256-of-canonical-atlas>
current_observation: <map-or-null>
hypotheses:
  - id: <content-id>
    source_ref: <source-id-or-null>
    cause: <variable-id>
    effect: <variable-id>
    relation: cochanges
    provenance: atlas | experience
    status: proposed | supported | refuted
    evidence: {supports: <int>, contradicts: <int>}
    supporting_evidence: [<experience-id>, ...]
    contradicting_evidence: [<experience-id>, ...]
experiences:
  - id: <monotonic-id>
    before: <observation>
    prediction: <forecast>
    action: <action-description>
    outcome: <machine-outcome>
    after: <observation>
    informative: <exact-json-boolean>
    comparison: <prediction-vs-observation>
```

Инварианты:

- experiences и evidence append-only;
- версия увеличивается один раз на каждый атомарно принятый полный переход;
- `observe()` без перехода версию модели не увеличивает;
- текущее наблюдение устанавливается только из внешнего `observe/step`;
- после detached load наблюдение считается runtime-статусом `stale/unbound`;
- подключение нового источника и первый `observe()` заменяют наблюдение без
  создания evidence;
- загрузка не должна выполнять повторную оценку старых переходов и не должна
  выводить `informative` из `before/after`; для ссылок evidence используется
  записанный и committed флаг;
- `experiences[].informative` обязателен, имеет ровно JSON boolean и входит в
  entry/state commitments (но не в prediction commitment); старые snapshots
  без него невалидны в строгом текущем `transition-shelf/v1` формате;
- повторная обработка одного experience id должна отклоняться и не менять
  состояние.

## 8. Канонизация и persistence

- canonical JSON: UTF-8, sorted keys, compact separators;
- перед вычислением `atlas_id` variables/actions сортируются по id, а
  hypotheses — по структурному content-id; исходный порядок массивов в hash не
  входит;
- hypotheses сортируются по content-id;
- experiences и ссылки evidence сортируются по монотонному номеру;
- timestamps, absolute paths, PID и platform-specific поля не входят в
  каноническую проекцию;
- перестановка YAML mappings и входных коллекций не меняет `atlas_id` и
  начальную каноническую shelf;
- запись атомарна через временный файл в том же каталоге и `os.replace`;
- ошибка или прерывание записи не повреждают последнюю валидную версию;
- load → save → load без нового перехода даёт побайтово тот же canonical JSON.

## 9. Порт внешней среды

Доменная логика зависит только от абстракции со следующими операциями:

```text
observe() -> {variable_id: scalar_value}
action_space() -> [action_description, ...]
step(action_id) -> {
  action_id: string,
  outcome: machine_value,
  obs_after: {variable_id: scalar_value}
}
```

Точная форма Python Protocol/ABC согласуется в предварительной записке.

Требования к границе:

- движок получает только данные указанной wire schema;
- `effects`, диагностические метки и дополнительные поля отклоняются;
- diff изменений вычисляет сам движок из `before/after`;
- объект реализации среды не является частью domain API;
- ошибки адаптера не должны изменять shelf частично;
- action выбирается только из `action_space()`;
- до `bind_observation()` runner получает и pure-валидирует raw `observe()`,
  raw `action_space()` и весь явный schedule; ошибка preflight не меняет shelf
  или уже pending prediction;
- выбор действия не входит в domain engine; минимальный runner принимает
  явный schedule либо обходит `action_space()` в стабильном лексическом порядке
  id исключительно для воспроизводимости, не извлекая из id семантику.

## 10. Запреты на специализацию под fixtures

В production-коде запрещены:

- сравнение с конкретными variable/action/source ids;
- таблицы заранее известных рёбер или результатов;
- ветвление по SHA-256 или полному содержимому atlas;
- логика, зависящая от числа переменных или действий в тестовом fixture;
- поиск смысла по prefixes, regex или лексике идентификаторов;
- зависимость от порядка YAML, mappings, variables, actions или hypotheses;
- чтение файлов, не переданных через публичный constructor/API;
- импорт модулей реализации внешней среды из domain layer;
- специальный путь выполнения для единственного демонстрационного YAML.

Одинаковая структура после взаимно однозначного переименования идентификаторов
и значений при подаче взаимно однозначно переименованной последовательности
действий/переходов должна приводить к изоморфной модели и прогнозу. Порядок
experience-журнала двух runner-прогонов не сравнивается, если переименование
изменило лексический порядок action id.

## 11. Обязательные тесты разработчика

### 11.1 Unit

- каждый validation code отдельным fixture;
- `cochanges`: support, contradiction и неинформативный переход;
- пороги policy со значениями 1, 2 и 3;
- атомарное рождение кандидатов с учётом первого перехода;
- отсутствие дублирования входного утверждения;
- переходы всех статусов;
- опровергнутое утверждение остаётся в shelf;
- прогноз `changed/unchanged/unknown`;
- duplicate experience id;
- canonical content-id и atlas-id;
- stale/unbound observation после reload;
- сбой атомарной записи.

### 11.2 Property/metamorphic

Автоматически генерировать валидные fixtures как минимум в диапазонах:

- 2–9 переменных;
- 1–4 действий;
- domains размером 2–4;
- 0–5 начальных утверждений;
- `support_min/refute_min` от 1 до 3.

Проверять:

- случайное переименование всех id и значений;
- перестановку YAML mappings и всех коллекций;
- повторный save/load;
- одинаковый переход, поданный в изоморфные fixtures;
- отсутствие необъяснимых различий после обратного переименования.

### 11.3 Integration

- fake environment реализует только публичный порт;
- прогноз обязательно записан до `step()`;
- два и более действия воздействуют на разные target-переменные;
- успешные и неуспешные outcomes перемешаны;
- процесс завершается, shelf открывается новым процессом, затем подключается
  новый fake environment;
- regression suite существующего проекта остаётся зелёным.

Тесты не должны состоять из одного фиксированного YAML. Минимум три вручную
заданных структурно разных fixture плюс property-generated набор.

## 12. Публичные критерии приёмки

Работа принимается, если:

1. все обязательные тесты проходят локально одной документированной командой;
2. модуль принимает любые валидные документы `transition-atlas/v1` в заявленных
   общих границах;
3. permutation/renaming не меняют структурный результат;
4. журнал и evidence не теряются после перезапуска;
5. canonical snapshot стабилен;
6. старые тесты репозитория не сломаны;
7. в коде отсутствуют fixture-specific ids, hashes и ограничения cardinality;
8. дополнительный набор валидных входов может быть подан без изменения кода.

Дополнительные входы при приёмке заранее не предоставляются. Это проверка
соответствия общему контракту, а не одному примеру.

## 13. Поставка

Разработчик передаёт:

1. предварительную записку по модулям и API;
2. реализацию изолированного движка;
3. полный набор unit/property/integration-тестов;
4. документацию обеих схем и публичного Python API;
5. CLI или минимальный runner для воспроизводимого локального прогона;
6. пример входа, созданный самим разработчиком и не используемый как
   специальный случай в реализации;
7. машиночитаемый JSONL-журнал демонстрационного прогона;
8. список известных ограничений и расхождений с данным ТЗ.

Коммит, push и merge выполняются только после отдельного подтверждения
заказчика.
