# DevOps-агент v2 — операбельный PDDL + numeric-память + декларативная онтология

## Откуда стартуем (итог v1)

v1 дошёл до **M7** и вердикта §8 — **ЖИВ**: `trials` падает (4→1), `oracle_calls→0`
(пик 1 на ep5, хвост 0), агент детерминирован (distinct=1 против 2 у LLM-baseline).
Гипотеза «саморемонт модели мира из провалов» доказана на узком кейсе (память/OOM + config).

v2 **не меняет гипотезу и не ослабляет критерий убийства** — он чинит *репрезентацию*,
чтобы модель стала операбельной и масштабируемой.

## Что именно лечим (диагноз)

В v1 три разных «хардкода», и важно их не путать:

1. **`compile_to_up` строит домен императивно** (UP API: `Fluent`, `InstantaneousAction`,
   `add_precondition`). Домена-как-объекта не существует — его нельзя `cat`, отредактировать,
   отдать будущему конструктору-редактору. Хуже: ветка `has_config` **переписывает сам домен**
   под инстанс.
2. **`world.py` if/elif (`exit_code==3 → unhealthy`)** — это **сенсор**, перевод реальности
   (docker State) в словарь симптомов. Его **нельзя** «парсить из PDDL»: PDDL знает предикаты
   планирования, но не знает `exit_code==3`. Это отдельный слой.
3. **Словарь симптомов/причин размазан по трём файлам**: `world.py` (obs→phase),
   `agent.py` (`_classify_symptom`, `_OBVIOUS_CAUSES`, `_FALLBACK_CAUSES`, применение фиксов),
   `oracle.py` (`CAUSES`). Это и есть «ужас» — лечится не PDDL'ем, а онтологией.

## Зафиксированные решения (с пользователем)

- **Единый always-on домен.** Один статичный `domain.pddl`. config-измерение всегда включено.
  Сервисы **без** config → `config_ok=true` для всех opt (нечего проверять). Сервисы **с** config →
  `config_ok` только для **подтверждённых** opt (см. «Закон модели»). Ноль ветвлений в коде.
- **Онтология во внешних YAML.** `ontology.yaml` — единый источник правды для sensor-правил,
  словаря симптомов/причин и `cause→repair`. Добавляем зависимость `pyyaml`.
- **Величины живут в обучении, планировщик — чисто логический (поправки M0 + #8).** Бакеты и числа
  убираются из домена совсем. «Сколько ресурса» (порог) агент **выучивает в мире** (удвоением) и
  применяет сам; «какое значение» (int/real/категория) — целиком забота обучения, в любом домене.
  В **домене** — только булевы предикаты (`mem_ok`, `config_ok`, …): «можно ли развернуть, учитывая
  что знаем?». **Ни стоимостей, ни `:metric`** — их нет. Минимизация уже сделана обучением, не
  планировщиком.
- **Движок — любой классический планировщик (Fast Downward, БЕЗ ENHSP).** Домен — чистый STRIPS
  (булева логика, без чисел) → нет вопроса «int или real», нет привязки к движку, поддерживающему
  numeric-costs. ENHSP не нужен; стоимости/метрика тоже не нужны. См. «Поправка #8».

## Закон модели v2 — «unknown → verify → trust» (на нём строится всё)

**Незнакомое НЕ считается рабочим, пока агент сам не проверил его интервенцией.** Это не фикс
одного бага, а общая позиция агента к незнанию — закон, которому подчиняются ВСЕ измерения.

Откуда взялся (диагноз M2-прогона): config-обучение в v2 не воспроизводилось — планировщик брал
`good` по тай-брейку, агент никогда не пробовал `bad`, ничему не учился. Оказалось, что и в v1
это «работало» лишь **случайно**: модель считала `config_ok=true` для ОБОИХ вариантов
(непроверенных), планировщику было всё равно, и он спотыкался о плохой конфиг только по удаче
тай-брейка. Закон убирает случайность: обучение становится **обязательным, а не лотереей**.

Как применяется единообразно:
- **память:** порог неизвестен → агент не доверяет, упирается интервенцией (OOM) → выучивает;
- **config:** домен пускает в `deploy` любой opt, что **не known-bad** (`config_ok = not known-bad`,
  как «бакет не known-unsafe» у памяти) — нужен только для *достижимости* (план есть ⇔ есть
  непровальный конфиг). **Мотив тронуть плохой opt — наследство** (вариант 1): агент застаёт
  сервис с уже применённым (incumbent) конфигом и действует по нему; мир либо подтверждает
  (running → incumbent обновляется), либо опровергает (unhealthy → `bad_config`, выбирается
  детерминированная непровальная альтернатива). Выбор конфига — **политика агента** (`_choose_config`),
  не планировщик: планировщик = exploit известно-безопасного, агент = explore наследства/неизвестного.
  Это та же петля, что у памяти; разный лишь природный повод (память — дешевизна, config —
  унаследованное состояние). Реализация — #7.
- **любое будущее измерение** (CPU, диск, версия, флаг) → тот же закон, без частных правил.

Следствие — **однородность модели:** один закон вместо домен-специфичных костылей (тай-брейки,
штраф-цены). Меньше частных случаев — меньше мест, где спрячется следующая такая же грабля.
M3 и далее строятся на этом законе. Прямой шаг к отложенному мета-домену «агент знает, чего не
знает». Реализация для config — #7.

## Архитектура v2 — три слоя, три источника правды

```
1. ПЛАНИРОВОЧНЫЙ ДОМЕН (PDDL)          devops_agent/pddl/domain.pddl     ← статичный, рукописный
   типы / булевы предикаты / actions       (цель будущего конструктора-редактора)
   (чистый STRIPS — без чисел и :metric)

2. ГЕНЕРАТОР ПРОБЛЕМЫ                   devops_agent/model/problem.py
   BiosState + goal → problem.pddl(текст) → PDDLReader.parse_problem() → up.Problem
   (проекция выученных знаний BIOS в :objects/:init/:goal; умеет дамп на диск)

3. ОНТОЛОГИЯ МИРА/ДИАГНОСТИКИ           devops_agent/model/ontology.yaml + ontology.py
   sensor-правила (obs→phase) · словарь симптомов · причины (CAUSES) · cause→repair
   (схлопывает ВСЕ if/elif из world.py / agent.py / oracle.py)
```

**Связь слоёв:** правило `cause→repair` из онтологии правит знания BIOS, которые проецируются в
булевы факты `:init` (`bad_config` → исключение из `config_ok`) либо используются агентом для
выбора величины (порог → объём памяти, подаваемый в мир). «Conditions» из твоего примера живут
как **данные** в онтологии и ссылаются на предикаты домена — не как `if/elif`.

## Поправка M0 — почему числа уходят из домена

M0 (risk-gate) сразу вскрыл архитектурную ошибку первой версии этого раздела. Исходно домен
делал `(assign (mem ?s) (min_safe_mem ?s))` и проверял `(>= (mem ?s) (min_safe_mem ?s))`. Но
после присваивания эта проверка тривиальна (равно) — **планировщик не делает никакого числового
выбора, значение ему просто диктуют**. То есть весь numeric-аппарат в домене — декорация. Плюс
именно на fluent-в-RHS (`FLUENTS_IN_NUMERIC_ASSIGNMENTS`) спотыкается `enhsp-opt` —
единственный движок с гарантией оптимальности. (Диагноз M0: парсинг ОК, но `enhsp-opt` не берёт
эту фичу; `enhsp` satisficing берёт, но без оптимальности → DoD не выполним.)

**Вывод:** числовой интеллект принадлежит **обучению**, а не планировщику. M0 убрал число из
*эффектов/предусловий*, оставив его как **стоимость**. Поправка #8 идёт до конца и убирает и
стоимость тоже — см. ниже.

## Поправка #8 — почему стоимость уходит из планировщика совсем

#8 (всплыл на M2-прогоне) показал следующий слой той же ошибки. FD-opt в оптимальном режиме
минимизирует стоимость **только целочисленную**; PDDL-тип `number` UP трактует как real
(`mem_cost → real`), и движок выдаёт `REAL_NUMBERS_IN_ACTIONS_COST not supported`
(`supports()=False`). Соблазн «раз память в MiB целая — заставим всех быть целыми» — домен-
специфичный костыль (другой домен даст дробную величину).

Корень глубже: **стоимость в планировщике — рудимент M0, который ничего не делает.** По факту
кода (M1+#7): объём памяти подаёт агент (`safe_buckets_for[0]`), конфиг — агент (`_choose_config`),
а от плана агент использует только «существует ли он» (да/нет); сами шаги и ценники игнорируются.
Метрика не различает ни одного плана (он один-единственный) — она инертна.

**Вывод:** минимизация уже живёт в **обучении** (удвоение находит минимальный рабочий размер), не в планировщике.
Стоимость/метрику убираем целиком. Это не заплатка про «int vs real», а снятие проблемы по корню:
**чисел в планировщике нет → нет и вопроса об их типе**, в любом домене. Реализация — #8.

## Доменная модель (чистый STRIPS, без чисел)

В домене — только булева логика: «можно ли развернуть, учитывая что знаем?». Никаких функций,
стоимостей и `:metric`.

```pddl
(define (domain devops)
  (:requirements :strips :typing :negative-preconditions)
  (:types service configopt - object)
  (:predicates
    (running    ?s - service)
    (mem_ok     ?s - service)                 ; память выделена (булево; «сколько» — у агента)
    (config_set ?s - service ?o - configopt)
    (config_ok  ?s - service ?o - configopt)) ; (s,o) не known-bad

  (:action set_mem
    :parameters (?s - service)
    :precondition (not (mem_ok ?s))
    :effect (mem_ok ?s))

  (:action set_config
    :parameters (?s - service ?o - configopt)
    :precondition (not (config_set ?s ?o))
    :effect (config_set ?s ?o))

  (:action deploy
    :parameters (?s - service ?o - configopt)
    :precondition (and (not (running ?s)) (mem_ok ?s)
                       (config_set ?s ?o) (config_ok ?s ?o))
    :effect (running ?s)))
```

Чистый STRIPS → решается любым классическим движком (FD без opt-метрики, и т.п.); вопрос
`int/real` не возникает.

**Кто что делает (честная граница):**
- **Планировщик** — *логика*: секвенирует `set_config → set_mem → deploy` и доказывает
  достижимость цели при текущих знаниях (план есть ⇔ есть `mem_ok`-путь и непровальный config).
  Чисел не касается.
- **Обучение** (петля агента) — *величины*: добывает порог интервенцией и **само** применяет его
  к миру (объём памяти, выбор config). Тезис проекта в силе: **учим модель мира, не политику**;
  планировщик потребляет логику модели, обучение владеет числами.

## Схема знаний BIOS (меняется под numeric)

Уходят `unsafe_mem`/`unsafe_svc` (множества бакетов). Приходят **пороги**:

```python
mem_threshold:     dict[str, int]   # workload_class → выученный min safe [MiB]  (класс-правило)
mem_threshold_svc: dict[str, int]   # svc_name      → per-service override       (карвинг M5b)
bad_config:        set[tuple[str,str]]   # как в v1
known_safe:        set[tuple[str,int]]   # подтверждённые (svc, mem) running
reverse_index:     dict[str, list[str]]  # как в v1 (НЕ засеваем — зарабатываем опытом)
```

Порог в домен **не проецируется** (чисел в домене нет). Он — знание агента: `_choose_mem(s) =
mem_threshold_svc.get(s) or mem_threshold[wc] or <текущий удваиваемый размер>` — агент **сам**
подаёт этот объём в мир. До первого знания — стартуем с `MEM_BASE` и удваиваем по результату
(см. «Петля обучения»). В `:init` идут только булевы факты (`config_ok` для не-known-bad opt, и т.п.).

## Петля обучения = удвоение до running (как живой девопс)

Не вычисляем порог до мегабайта. Делаем как обычный девопс: **мало памяти → дай вдвое →
ещё мало → ещё вдвое → ожило → стоп.** Первый сработавший размер и есть ответ.

- старт с базы `MEM_BASE` (напр. 64 MiB); проба → если `oom_killed`, **удваиваем** и пробуем снова;
- первый `running` → это `mem_threshold` (агент его запоминает и подаёт в мир);
- **правило, а не таблица:** размеры порождаются удвоением (`base·2^k`), без потолка и без
  захардкоженного списка [64,128,256,512,1024]. Этим M3 принципиально ≠ v1-бакеты: правило
  обобщается на любой сервис/масштаб, фиксированный список — нет.
- перенос на новый сервис того же класса → берём выученный размер → 1 проба (как M4);
- карвинг (M5b): сервис того же класса не завёлся на классовом размере → per-svc продолжаем
  удваивать дальше, классовое правило не ломаем.

Минимум — «минимальный стандартный размер» (степень двойки), а не точный байт. Это сознательно:
точность ±мегабайт — преждевременная оптимизация (вернёмся, если «СТО затопает»).

Метрики §8 сохраняются: trials-to-converge = число удвоений (первый раз `O(log)`, повтор → 1);
oracle-кривая, детерминизм, человеко-правки — без изменений.

## Онтология (YAML-схема)

```yaml
sensors:                       # реальность → словарь симптомов (заменяет world.py if/elif)
  - when: {oom_killed: true}            then: oom_killed
  - when: {exit_code: 0}                then: running
  - when: {exit_code: 3}                then: unhealthy
  - default:                            error
symptoms: [running, oom_killed, unhealthy, error]
causes:   [memory, config]              # источник CAUSES для oracle.py
obvious:  {oom_killed: memory}          # _OBVIOUS_CAUSES — оракул не нужен
fallback: {unhealthy: config}           # _FALLBACK_CAUSES при oracle=None
repair:                                 # cause → как править BIOS (ссылается на предикаты домена)
  memory: {kind: numeric_threshold, store: mem_threshold, carve: true}  # → объём подаёт агент
  config: {kind: set_member,        store: bad_config}                  # → config_ok (булев) в :init
```

Один файл — единственный источник правды. `world.py`, `agent.py`, `oracle.py` читают его,
никаких локальных таблиц-словарей.

## Честные риски v2

- ~~ENHSP-доступность~~ — **снято**: ENHSP убран, движок FD-opt уже доказан в v1 (M2/M7).
- **«Тонкая» роль планировщика** — при одном сервисе план тривиален, минимизировать нечего
  (стоимость одна). Это осознанный размен (см. «Поправка M0»): числовой выбор — в обучении, не в
  планировщике. Ценность планировщика проявляется на реальных альтернативах (несколько
  сервисов/конфигов/стратегий); надо не выдавать planning за самоцель там, где выбора нет.
- **Детерминизм планировщика** — метрика B (distinct=1): FD-opt детерминирован, но сравнение всё
  равно нормализуем **по стоимости плана**, не по строке (на случай равно-оптимальных перестановок).
- **Round-trip PDDL-текста** — детерминированный порядок объектов/инициализации сохранить
  (как в v1), иначе плывёт сравнение планов.
- **Сходимость удвоения** — удвоение всегда завершается (рано или поздно памяти хватит), но нужен
  разумный предохранитель сверху (напр. потолок реальной машины), чтобы не уйти в бесконечность на
  заведомо нерабочем сервисе.

## Открытый вопрос на потом (НЕ в этом заходе)

Мета-домен (эпистемическое планирование экспериментов: планировщик сам решает, *какую* пробу
ставить) — по-прежнему отложен. v2 оставляет удвоение захардкоженным в петле, как v1 оставлял
бинарный поиск по бакетам.
